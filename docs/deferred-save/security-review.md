# Deferred ticket save: security review notes

Deferred ticket save is a new write path for tickets. Instead of the classic editor's AJAX calls and the block editor's REST calls per ticket, both editors send one `tec_tickets` payload with the post save, and one server handler applies it. This note is for the SVUL reviewers: where a request enters, what refuses it and where, and which test shows each refusal. Linear: SOFT-4822 and its sub-issues SOFT-4823 to SOFT-4828. Plans: the `soft-4823` to `soft-4828` changes in `the-events-calendar/plans`.

## Where a payload enters

| Entry point | Request | Reads | Class |
|---|---|---|---|
| Classic editor | `POST wp-admin/post.php` (the post form) | `$_POST['tec_tickets']`, `$_POST['tec_tickets_nonce']`, `$_POST['post_ID']` | `src/Tickets/Deferred_Save/Classic_Save.php`, on `save_post` at priority 20 |
| Block editor | `POST /wp/v2/{type}/{id}` and `POST /wp/v2/{type}` (the post save) | `$request['tec_tickets']` | `src/Tickets/Deferred_Save/Block_Save.php`, on `rest_after_insert_{type}` at priority 200 |

Both call `Commit::run( $raw, $post_id )` (`src/Tickets/Deferred_Save/Commit.php`). Nothing else reads the payload. No REST endpoint was added.

## The payload

```
tec_tickets = [
    update => [ ticket ID => data ],
    create => [ data, data ],
    delete => [ ticket ID ],
    move   => [ ticket ID => destination post ID ],
]
```

`data` is the array Event Tickets' `ticket_add()` accepts today. It is passed through, with two exceptions applied by the parser (`Payload/Parser.php`): `ticket_id` inside `data` is overwritten by the entry key on `update` and removed on `create`, because `ticket_add()` reads the ticket to write from it. `Commit` also removes `tec_tickets_create_key` and `tec_tickets_duplicate_of` from a `create` entry's `data` before the provider sees it (see step 7). An `update` replaces the ticket: a value its `data` leaves out is saved empty, except the type and the menu order, so both editors send the whole ticket.

## The order of checks

1. **Classic only, `Classic_Save::on_save_post()`**: the post has not been committed earlier in the same request (a post re-saved inside its own `save_post`, as TEC does when "Sticky in Month View" changes, is committed once), not an autosave, not a revision, not a REST request, the post type is ticketable, `tec_tickets` is present, `tec_tickets_nonce` is present, the request is not a preview (`wp-preview=dopreview`: previewing a draft saves the draft itself through `post_preview()`, and the page keeps its staged changes for the real save), `post_ID` equals the post being saved, and the nonce verifies (user-bound, action `tec_tickets_deferred_save`). When the nonce does not verify, nothing is applied; a notice says so only when the post form's own nonce (`_wpnonce` for `update-post_{ID}`, as `post.php` verifies it) does, for a user who can edit the post: `nonce_life` is filtered per action, so a site can make this nonce expire before the form's. Any other request gets no notice. The classic editor writes `tec_tickets_complete` after its last staged field; PHP drops the fields past `max_input_vars` in the order they arrive, so a request without it lost part of its payload, and nothing of it is applied (a notice says so). Heartbeat refreshes `tec_tickets_nonce` with the post form's own nonces (`Classic_Save::refresh_nonce()` on `wp_refresh_nonces`, only when core refreshed them for a user who may edit the post), so an edit screen left open does not lose its staged changes to an expired nonce. The feature as a whole is on unless `Controller::is_active()` is switched off through the `TEC_TICKETS_DEFERRED_SAVE_DISABLED` constant or environment variable or the `tec_tickets_deferred_save_active` filter; there is no per-post switch. The post form's own nonce is not used because ECP rewrites the post ID on a split save; `post_ID` is rewritten with it, which is why the binding is to `post_ID`.
2. **Block only, `Block_Save::on_rest_after_insert()`**: reached only through the core posts controller, behind its `update_item_permissions_check` / `create_item_permissions_check` (`edit_post`). The hooks are attached per ticketable type when the feature registers and again on `rest_api_init`, for a type made ticketable later. Any authentication core accepts reaches it: cookie auth with `X-WP-Nonce` from the editor, and Application Passwords from API clients. That is wider than the legacy `tribe/tickets/v1` endpoints, whose body nonce in practice requires a cookie session; the capability and ownership checks below are the same whichever way the user authenticated. Not on the autosaves route. The result is added only to the response of the request that committed it, so a second save or read of the same post in a `/batch/v1` request gets no answer of its own, and each answer carries a per-save `id`, so the editor can tell two equal answers apart. The hooks are attached per ticketable post type, so a payload sent with a non-ticketable type is never read and the response carries no `tec_tickets` field.
3. **`Payload\Parser::parse()`**: root must be an array with only the four parts; IDs are positive integers or digit strings; `data` must be an array; a ticket named in more than one of `update`, `move` and `delete` loses every entry. A rejected entry is dropped and recorded in `Payload\Rejections`; a malformed root or unknown part throws `Payload\Malformed_Exception`, which `Commit` answers with one payload-level error.
4. **`Commit::run()`**: the post ID is normalised through `Event::filter_event_id()`, as the AJAX save does. Total entries across parts capped at 100 (`tec_tickets_deferred_save_max_entries`), counted on the raw payload before parsing, invalid entries included, so no payload makes the parser work through more than the cap; whole payload rejected above it.
5. **`Checks::run()`**: the current user holds `edit_post` on the post, through `Ticket_Permissions::user_can_edit_tickets_of()` and its `tec_tickets_user_can_edit_tickets_of` filter, or the whole payload is rejected. Every `update`, `delete` and `move` ticket ID must resolve through its provider to a ticket whose post type is the provider's ticket type and whose event is the post being saved (an attendee, a page, another post's ticket and a missing ID are all rejected per entry). Every `update` and `move` needs `user_can_edit_ticket()` and every `delete` `user_can_delete_ticket()`, which also requires `delete_post` on the ticket; the legacy `tribe_tickets_current_user_can_delete_ticket` filter takes no user, so it is not asked. Every `move` destination must be a post the user can edit. A `create` that names `tec_tickets_duplicate_of` must name a ticket on the post that the user can edit, since its copy carries every meta of that ticket. A rejection for a ticket that is not on the post carries `not_on_post`, so the editors do not show that ticket again.
6. **Routing seam**: `tec_tickets_deferred_save_routes` may send entries to other posts (mini-project D). Any payload other than the one the checks returned, and any payload routed to another post, is run through `Checks::run()` again against the normalised post it is written to. A route key must be an integer post ID and every key in a routed payload an integer; anything else is skipped, and every checked entry that no route handed out is reported as not saved.
7. **Replay**: `update`, `create`, `move`, `delete` (creates before moves, so a copy is taken while its source is still on the post), each entry guarded so an exception inside a provider becomes that entry's error and never a 500; the guard also turns off the manual-update flag `ticket_add()` leaves on when it throws. An exception after a write took effect is logged and does not hide the write, and the entry's error is marked `applied`: a create or update whose `tribe_tickets_ticket_added` listener threw once the provider returned; a delete that threw once the ticket was gone; a move that threw once the ticket was on the destination, whose attendees may not have moved, since a listener of the moved action moves them. A create or update that throws inside the provider is reported as not saved, not `applied`, whatever part of it was written, because what the provider wrote is not known. Such a create whose ticket is on the post, a copy made through `duplicate_ticket()` included, is still reported with its ID, found by comparing the provider's tickets on the post before and after, whichever listener threw (RSVP relates the ticket in `meta_input`, before any `save_post` listener runs), as long as it is the only ticket new on the post: the editor then saves it again as an update of that ticket, never as a second ticket. Sending the same update again is safe: the block editor keeps the entry staged, and the classic notice asks for it again, or, for a ticket created but not finished, to edit that ticket. A `create` entry may carry `tec_tickets_create_key`, 8 to 64 letters, digits and dashes; the ticket it creates keeps it in `_tec_tickets_deferred_save_create_key`. A later `create` with the same key on the same post is saved over that ticket, through `Checks::run()` as the update it is, and reported as created at its position, even when that update throws, so a save whose answer was lost is sent again without creating its tickets twice. The key is looked up only among the provider's tickets on the post being saved, and `Tribe__Tickets__Tickets::duplicate_ticket()` does not copy it. `create` resolves its provider from `data['ticket_provider']` through `Tribe__Tickets__Tickets::get_ticket_provider_instance()`, which only returns active modules; `update`, `delete` and `move` resolve the provider from the ticket, never from `data`. Each entry's `data` reaches `ticket_add()` as the AJAX save hands it over: there `tribe_get_request_var()` runs `tribe_sanitize_deep()` over the URL-encoded `data` string before it is parsed, which strips nothing, so the providers and WordPress do the sanitising on both paths; `ticket_type` is sanitized as `Metabox::ajax_ticket_add()` does. A Tickets Commerce or PayPal price that is negative or not a number is refused per entry, as the block editor's ticket endpoint refuses it. A move to a post that is not of a ticketable type, or is trashed, `inherit` or `auto-draft`, is refused. A `create` with `tec_tickets_duplicate_of` is made by that ticket's provider through `duplicate_ticket()`, which copies the meta no edit form carries, and the entry's fields are then saved over the copy as an update. The same functions run as today: `ticket_add()`, the provider's `delete_ticket()`, `Move_Ticket_Types::move_ticket_type()`, plus the `tribe_tickets_ticket_added` and `tribe_tickets_ticket_deleted` actions the replaced callers fire.

## What the editors add

- Classic (`src/resources/js/deferred-save.js`): staged rows are cloned from server-printed `<template>` elements and filled through `textContent`; a duplicated ticket's form is parsed with `DOMParser` and only read, and the staged copy names the saved ticket it copies; field names are matched by attribute comparison; the open edit panel's inputs are disabled on submit so they never post as top-level fields (ETP's `Meta::save_meta` falls back to `$_POST` for them). The rejected-ticket notice (`Classic/Notices.php`) is a per-user transient and names a ticket only when it is a ticket on the saved post, so a payload cannot probe other posts' titles; changes marked `applied` are listed under their own heading, which says they need not be entered again; a create reported with an ID but not saved is listed under another, named as the ticket it is through the same on-post check, which asks the admin to edit that ticket and not add it again.
- Classic, continued: a saved ticket carries one staged change at most (move refused while an edit is staged, edit while a move is staged, delete replaces either), and a submit that would carry more fields than `max_input_vars` is refused rather than truncated by PHP. Each staged new ticket carries a random key from the moment it is staged, kept across edits, so a form the browser sends again does not create its tickets twice. Staged prices and sale prices are sent as the plain number read with the site's decimal separator, so a price such as `12,50` on a comma-decimal site is not refused as invalid; one that cannot be read is sent as typed and refused.
- Block (`src/modules/data/blocks/ticket/deferred*.js`): the payload builder drops `__proto__`, `constructor` and `prototype` segments and descends only through own properties, and never names a ticket in two parts; the payload is rebuilt on `editor.preSavePost` from the blocks that exist, and what it carries is recorded, positions included; if that fails, no payload is sent and the changes stay staged; the response is applied once, to exactly what was sent (`reconcileSaveResponse()`), so changes staged while the request was in flight stay staged and a block changed since is not reloaded over; a payload-level refusal keeps every sent change staged with its message; a refused delete or move is shown as an editor notice and the ticket's block comes back, unless the refusal is marked `not_on_post` or a block holds the ticket already, while one whose error is marked `applied` happened and brings back no block; a block Undo brings back takes its staged delete or move out of the staged changes, so removing the block again with the editor's toolbar does not send them; a create or update whose error is marked `applied` is settled as saved, its hook fires and the error stays on the block as a warning; a create answered with an ID and an error not marked `applied` gets the ID and stays staged, so the next save sends its fields as an update of that ticket; a staged ticket whose latest edit fails the shared rules is left out of the save and keeps its staging and its error; each create carries its block's client ID as its key; only a Ticket block's move is staged, an RSVP moves at once as its other changes do; lifecycle hooks receive the details each ticket was sent with and run isolated after the store is settled; error messages render as React text; the payload edits stay out of the undo stack; a draft's preview, a real save whose answer is never applied, leaves the payload out; a save that created tickets writes their IDs into the blocks as soon as its answer arrives and, once it has finished, is followed by one more save without a payload, so the post content has their IDs and whatever is still staged waits for the next save; ET+ attendee fields, which its Ticket Presets add to the body as JSON, are sent as the list the ticket save reads.

## Deliberate choices a reviewer may question

- **User-bound nonce on the classic path.** ECP rewrites the post ID on a "This event" / "This and following" save, so a post-bound nonce cannot be verified inside `save_post`. The `post_ID` binding is what ties the payload to one post; ECP rewrites it with the post.
- **Only `edit_post` opens the post.** `Metabox::has_permission()` also accepts `edit_event_tickets` or the type's `edit_others_posts`. Community Events grants `edit_event_tickets` to every logged-in user by default, so that rule admits any subscriber to any post; `edit_others_posts` is covered by `edit_post`, which `map_meta_cap()` maps to it for someone else's post. The legacy AJAX and REST paths still use the old rule.
- **Sanitisation is the providers' and WordPress's**, exactly today's AJAX path, where `tribe_sanitize_deep()` runs over the encoded `data` string and strips nothing. A user with `unfiltered_html` keeps markup in a ticket's name and description, as on the AJAX path; `ticket_sku` reaches meta as the AJAX path leaves it. Running `tribe_sanitize_deep()` over the parsed fields instead stripped every description's HTML on each save.
- **The move destination** must be a post the user can edit, of a ticketable type, and not trashed or a draft placeholder; `move_ticket_type()` itself only rewrites the ticket's event meta. The legacy AJAX move checks no capability at all.
- **A Contributor cannot delete tickets, even on their own draft.** Tickets are published posts, so `delete_post` on a ticket maps to `delete_published_posts`, which Contributors lack. They can still create and edit tickets on a post they can edit. `Checks_Test` pins this.
- **A save that creates tickets in the block editor saves the post twice.** The created IDs arrive with the save's answer, after the content was written, so the editor saves once more to store them in the blocks; without it a reload showed an empty block next to the saved ticket. The second save carries no payload, but it does save any other change made to the post while the first was out.
- **A provider that throws after inserting a ticket post but before attaching it to the post** has the entry reported as failed: the orphan is not a ticket of the post, so it is neither shown nor duplicated there. Tickets Commerce relates its ticket after the insert, so it can leave one; RSVP relates it in the insert itself, so its ticket is on the post and reported with its ID. The legacy AJAX save answers both with a 500.
- **Create keys are chosen by the client.** A key reaches only a ticket of the same provider on the post being saved, and the save over it passes the same checks as an `update` of that ticket, so a guessed key gives nothing that user could not do through `update`. Keys are a block's client ID (a UUID) or a random token per classic row.
- **A create key guards a retry, not a race.** It is looked up before the insert and written after it, with no lock: two requests with the same key in flight at once can both create, as every retry did before keys, and so can a failure between the insert and the key write. Neither editor lets a second save start while one is in flight. A ticket moved to another post or deleted since is not found, so the create runs again; the lookup stays on the saved post on purpose. A create sent again carries the editor's latest values and is saved over the ticket like any update: last write wins, as for every update, and WordPress's post lock warns a second editor off the post.
- **A create whose provider throws is saved again even when its writes finished.** A listener inside `ticket_add()` that throws after the provider wrote everything cannot be told from one that threw halfway, so the entry is reported as not saved and the editor sends the same values again as an update, which runs the update listeners once more. Telling them apart would need each provider to report how far its save got.
- **A ticket new on the post is taken as the create's** when the provider throws. A listener that adds another ticket to the same post and then throws, before the create's own ticket exists, would have that ticket reported as the create's; with two new tickets the entry is reported as failed instead.
- **A partly applied move is reported, not repaired.** When a listener of the moved action throws, the ticket is on the destination and its attendees may still be on the source: the result says so, and the attendee list's move tool is the way to finish it. Running the move again would repeat what already ran, notifications included.
- **Nonce feedback only on the admin's own form.** A classic save whose deferred-save nonce does not verify applies nothing. It says so only when the post form's own nonce verifies for a user who can edit the post: heartbeat refreshes both nonces together, but `nonce_life` is filtered per action, so they can expire apart. A request without that proof gets no notice, so a forged one learns nothing.

## Open items for mini-project D

- Which post a routed payload lands on after a split is D's; the seam re-checks against the destination, so D cannot widen what the user may do.
- The classic seam runs at `save_post` priority 20, before ECP commits occurrences at `redirect_post_location` 100; if D needs the occurrences it moves its hook, not the checks.
